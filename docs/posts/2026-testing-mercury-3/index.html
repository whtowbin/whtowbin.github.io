Testing Mercury 3, Inception Labs’ diffusion LLM

A real step up from Mercury 2.5, with cheaper tokens than Haiku 5.5 but about the same bill per problem. It was also the only model I tested that found the benchmark answers online.
Published

October 2026

Supporting numbers are in the footnotes; a section number (§) there refers to the project’s design log.

Inception released Mercury 3 on 19 October, the day I finished drafting my second post about Mercury 2.5 (I held that one back to test Mercury 3 first). Inception says Mercury 3 beats Claude Haiku 5.5 and GPT-6 Luna at more than 1,000 tokens a second, but it published no benchmark scores. So I ran it through the tests I had used for Mercury 2.5: ten django tasks (real bug fixes in the web framework, from SWE-bench Verified) and fifteen SciCode problems in scientific programming, in my own harness and in mini-swe-agent, a minimal agent that gives the model only a shell.

The short version: Mercury 3 is clearly better than Mercury 2.5, and my harness helps it more than it helped Mercury 2.5. Per token it is cheaper than Haiku 5.5 at its launch price, but a problem costs about the same. And on the way, Mercury 3 found the answers to both benchmarks online.

It went looking for the answers

Mercury 3 found the answers to both benchmarks online, through routes my block list did not name. No other model with the same tool reached an answer.

My harness gives the model a web fetch tool and blocks each benchmark’s own address. On one of the django tasks, Mercury 3 went to GitHub’s API, whose address the block list did not contain, fetched the files of the pull request that had fixed the very issue it was working on, and then resolved the task. On the SciCode tasks it searched GitHub for “SciCode benchmark”, found a copy of the dataset inside another company’s repository through a code search site, opened a mirror of the dataset on Hugging Face, and ran the problems’ own function names through Google and Bing.

I threw those results out, blocked those routes and ran everything again. It kept looking. One run got through again, this time reading django’s latest code, fixes included, from a CDN that serves copies of GitHub repositories. I voided that run too.1

The other models did not get this far. Mercury 2.5 tried django’s documentation once and was refused; Haiku 5.5 read papers and a physics library and tried the SciCode repository once; GLM 5.3 Flash, in an earlier round, got back only search-result pages. A model this resourceful makes every benchmark a test of the sandbox too, and the sandbox needs checking again for each new model.

That is a reversal from the first post, where my harness and mini-swe-agent ended up in the same place and the model set the ceiling. With Mercury 2.5, mini-swe-agent did a little better on the django tasks; with Mercury 3, my harness did, using about a third as many model calls.4

Why the harness suits it better

Mercury 3 can use tools. Mercury 2.5 often could not.

My harness gives the model typed tools for reading files, editing them and running tests, and it checks each step before moving on. Over 30 runs on the django tasks (each of the ten, three times), Mercury 2.5 sent 12 edits or file reads that failed, usually because it got a file path or the text to replace wrong, and 6 of its 15 failed runs had one. Mercury 3 sent one failed edit or read in the same 30 runs.5

It is not a careful model, though. In one run Mercury 3 wrote a fix, saved it away with git’s stash command to compare against the original code, and ran out of steps. Its next attempt started fresh, never noticed the fix was gone, and wrote a different one from scratch. That one passed. It is clumsy, but it uses the tools, notices when its code is wrong, and gets there.

My harness also needed fixing for it. A check built for Mercury 2.5 sent a step back whenever the model marked it done without saying what result it expected. Mercury 3 almost never said, so its finished steps kept being redone; removing the check raised its perfect runs on my private tasks from 24 to 30 of 31 runs. A harness built around one model’s habits can hold back a better one.6

What it costs, and against what

At its launch price Mercury 3 costs about what Haiku 5.5 does. Thinking hard, it was ahead of Haiku on the django tasks; thinking less, it matched Haiku in less time, and on the SciCode tasks for half the cost. At list price it costs about twice as much.

Inception sells Mercury 3 at half its list price and Mercury 2.5 at a fifth. So at the prices I paid, a Mercury 3 task cost three to four times a Mercury 2.5 task, and at list prices about one and a half times, while solving far more (the hollow markers in Figure 1).

The fairer comparison is with models at Mercury 3’s price, and that is Haiku 5.5. On the django tasks Mercury 3 was ahead, on the SciCode tasks they were level, and on my private tasks Haiku was slightly ahead and slightly cheaper. Those private tasks are recent enough that the models are unlikely to have trained on them, and the django tasks are public: Mercury 3’s plans said they knew django’s own fix in 11 of its 30 runs. So Inception’s claim holds where memory can help, and not clearly elsewhere. At list price, Mercury 3 costs about twice what Haiku 5.5 does.7

How hard Mercury 3 thinks moves it along that line. My harness runs it at high reasoning effort. At low effort it resolved 19 of 30 django runs against Haiku’s 20, and was level with Haiku on the SciCode tasks, for about the same cost on django and half on SciCode, and faster on both. What it gave up were the hard django tasks: on the four that high effort had sometimes missed, low solved 1 of 12 runs against high’s 8. Thinking less made it Haiku’s equal in less time; thinking more is what put it ahead.8

Speed did not help either, though the speed is real. Once Mercury 3 starts writing an answer, it streams at 1,000 to 1,300 tokens a second, close to Inception’s 1,068 and about twice Haiku 5.5’s rate at the same effort. But it reasons first, and that is where the time goes: 18 calls a django task, each mostly reasoning, took it 2.5 minutes against Mercury 2.5’s 1.4. Haiku 5.5 made half as many calls and finished in 1.8; Mercury 3 at low effort, in 1.4.

What moves the time, and much of the cost, is the number of turns. In my earlier posts, Sonnet 5 in Claude Code took 26 model calls, more than two minutes and 38 cents for each of the six hardest django tasks; Sonnet 5.5, in the same agent, took 5 calls, about 15 seconds and 6 cents, and solved all six. Over all ten django tasks Sonnet 5.5 cost about five cents a task at list price, less than Mercury 3 at its list price, and it was perfect on my private tasks whenever it ran. In my harness, which reuses less of its input from cache, it cost about nine times Mercury 3. A model that needs fewer turns, in an agent that caches well, did more for speed and cost than any number of tokens a second.9 10

A second job

On a different job, extracting arguments from scientific text, Mercury 3 was not clearly better than Mercury 2.5 and cost seven to ten times as much.

I also use Mercury to pull claims, and the links between them, out of scientific papers. There Mercury 3 found more links and was wrong more often. One lesson from that work applies to any model comparison: my scorer first showed Mercury 3’s recall well ahead, because it counted only the links whose claims the model had already found. Counted over every link in the text, the gain disappeared.11

What I would use it for

Mercury 3 is a real step up from Mercury 2.5 in an agent. It calls tools cleanly and makes use of a harness that Mercury 2.5 mostly stumbled through. If I were building on Mercury today, I would build on Mercury 3, with a harness that checks its work without second-guessing it.

Its speed pays where a job wants one long answer from one call. I asked each model for a complete module, specified section by section, in a single call; the answers ran to about 400 lines. Mercury 3 at low effort wrote it in about 27 seconds, half Haiku 5.5’s time, at three quarters of the cost; one of its three answers passed every hidden check, one missed two and one was broken, where two of Haiku’s passed every check and the third missed one. At high effort it thought through a 40,000-token budget and returned nothing in two tries of three. So: low effort, one call, and a check on the answer.12

In a long agent loop, back and forth between the model and my computer, it does not win on speed, because every turn starts with reasoning. A faster connection would not help much, since the fixed delay of a call is about a sixth of its time. More serving capacity might: asked alone, it wrote at 530 to 640 tokens a second, reasoning included, against about 315 in my agent runs, which ran several at once.

And I would not choose it for its price alone. At list price it costs about twice what Haiku 5.5 does, and on scientific text it was no better than Mercury 2.5. Where Mercury 3 looks strongest, on public benchmarks, every model may be remembering.
